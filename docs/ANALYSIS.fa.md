# تحلیل فنی و برنامهٔ توسعهٔ SQL Server Performance Observatory

[README انگلیسی](../README.md) · [README آلمانی](../README.de.md) · [گزارش آزمون](en/testing.md)

نسخهٔ سورس: `0.1.0-preview.1` — تاریخ آماده‌سازی: ۵ اکتبر ۲۰۲۶.

## ۱. مسئله‌ای که این محصول حل می‌کند

این پروژه برای پاسخ به چهار پرسش ساخته شده است: کدام Query در مقایسه با گذشته کندتر شده است؟ آیا مجموعهٔ Planهای مشاهده‌شده تغییر کرده است؟ چه نشست‌هایی منتظر یکدیگر هستند؟ از Deadlockهای رخ‌داده چه شاهد قابل نگهداری داریم؟

هدف، جایگزینی کامل SQL Server Management Studio یا ابزار حرفه‌ای مانیتورینگ نیست. هدف این نسخه، ارائهٔ تحلیل قابل توضیح، خواندن داده با مجوز مشخص، تفکیک خطا از نبود داده و یک آزمایش تکرارپذیر است. پیشنهاد اصلاح نباید به اجرای خودکار تغییر در محیط عملیاتی تبدیل شود.

مخاطب اصلی، توسعه‌دهندهٔ بک‌اند یا DBA یک تیم کوچک است. این انتشار مدل تک‌تحلیلگر دارد: هر فرد دارای کلید دسترسی برنامه، داده‌های تمام Targetهای پیکربندی‌شده را می‌بیند. کنترل دسترسی چندکاربره، چندمستاجری یا مجوزدهی جداگانه برای هر دیتابیس در این نسخه وجود ندارد.

## ۲. محدودهٔ تحویل و مرز تأیید

سورس شامل هستهٔ C#، آداپتور SQL Server، میزبان ASP.NET Core، رابط سه‌زبانه، ابزار مستقل آزمایش، فایل‌های استقرار و آزمون‌هاست. این مجموعه، طرح معماری بدون کد یا صرفاً داشبورد با اعداد ثابت نیست؛ مسیر Live برای جمع‌آوری از SQL Server نوشته شده و مسیر Replay برای نمایش بدون دیتابیس صریحاً از آن جداست.

بااین‌حال SDK دات‌نت، SQL Server و Docker در محیط تولید این سورس موجود نبودند و دریافت SDK نیز به‌دلیل محدودیت شبکه ممکن نشد. در نتیجه کامپایل C#، اجرای میزبان ASP.NET، xUnit، اتصال واقعی به SQL Server و سناریوی اندازه‌گیری در این محیط تأیید نشده‌اند. بررسی سورس یا موفقیت رابط آزمایشی، جای Build و آزمون یکپارچه را نمی‌گیرد. وضعیت دقیق در [گزارش آزمون](en/testing.md) و [گزارش ماشینی](qa/delivery-validation.json) ثبت شده است.

## ۳. معماری و دلیل جداسازی اجزا

```text
SQL Server: Query Store / DMVs / existing XEL
                   |
                   v
Observatory.SqlServer: typed, parameterized collectors
                   |
                   v
Observatory.Core: analysis / normalization / local snapshots
                   |
                   v
Observatory.Web: background worker / authenticated APIs / UI

Observatory.Lab: separate executable, local laboratory writes only
```

هسته به HTTP یا Driver دیتابیس وابسته نیست. فرمول‌ها، زنجیرهٔ Blocking و تبدیل XML در کلاس‌های مستقل قرار دارند. آداپتور SQL فقط چهار Query ازپیش‌تعریف‌شده و پارامتری دارد. سرویس وب endpoint اجرای SQL دلخواه ندارد و ابزار آزمایش را به‌عنوان وابستگی وارد نمی‌کند.

برای این دامنه از ORM استفاده نشده، زیرا هدف، خواندن قراردادهای مشخص سیستمی SQL Server است، نه CRUD روی مدل‌های کسب‌وکار. ذخیرهٔ Snapshotها نیز در فایل‌های محلی با تعویض اتمیک انجام می‌شود تا برای مشاهدهٔ یک دیتابیس، الزام نصب دیتابیس دوم ایجاد نشود. این انتخاب برای پیش‌نمایش تک‌نمونه‌ای مناسب است؛ راهکار HA یا آرشیو تحلیلی حجیم نیست.

## ۴. تحلیل صحیح Query Store

محاسبهٔ میانگین باید با تعداد اجراها وزن‌دهی شود. مثال کاملاً فرضی: یک بازه ۱۰۰ اجرا با میانگین ۱۰ میلی‌ثانیه دارد و بازهٔ دوم ۲ اجرا با میانگین ۱۰۰۰ میلی‌ثانیه. میانگین صحیح تقریباً ۲۹٫۴۱ میلی‌ثانیه است، نه ۵۰۵ میلی‌ثانیه.

```text
weightedMeanMs = sum(executionCount * intervalAverageMs) / sum(executionCount)
```

دادهٔ زمان Query Store برحسب میکروثانیه خوانده و یک‌بار به میلی‌ثانیه تبدیل می‌شود. Logical Reads به‌عنوان تعداد Page گزارش می‌شود، نه میلی‌ثانیه یا نرخ انتقال دیسک. آداپتور ردیف‌های آماری مربوط به یک Plan و Interval را پیش از تحلیل تجمیع می‌کند. برای مبنای این قراردادها به [مستند رسمی runtime stats](https://learn.microsoft.com/en-us/sql/relational-databases/system-catalog-views/sys-query-store-runtime-stats-transact-sql?view=sql-server-ver17) مراجعه کنید.

جمع‌آوری تکراری، نسخهٔ کامل مجموعهٔ مشاهده‌شده را جایگزین می‌کند؛ شمارنده‌های یک بازه در هر Poll دوباره به تاریخچه اضافه نمی‌شوند. فقط اجراهای موفق ثبت‌شده و بازه‌های بسته وارد مقایسه می‌شوند. بازه‌ای که مرز دو پنجره را قطع می‌کند به نسبت زمان تقسیم نمی‌شود؛ کنار گذاشته شده و هشدار دارد.

مبنای پیش‌فرض، دو پنجرهٔ ۶۰ دقیقه‌ای است. آخرین بازهٔ بستهٔ سرور نقطهٔ انتهایی مقایسه را تعیین می‌کند. برای هر Query/Context/Hash، میانگین، تعداد اجرا، CPU، Logical Reads و مجموعهٔ Planها محاسبه می‌شوند.

قاعدهٔ پیش‌فرض «نامزد بررسی افت عملکرد» نیازمند حداقل ۱۰ اجرا در هر طرف، میانگین مبنای حداقل ۱ میلی‌ثانیه، نسبت حداقل ۲ و افزایش مطلق حداقل ۲۵ میلی‌ثانیه است. این‌ها آستانه‌های تحلیلی‌اند، نه محدودیت تجاری. کمبود داده یا قطع‌شدن نتیجه به‌علت سقف ردیف، با وضعیت نامشخص نمایش داده می‌شود.

این قاعده آزمون آماری علیت نیست. تغییر پارامترها، بار هم‌زمان، حجم داده، Cache و روش Capture می‌توانند روی نتیجه اثر بگذارند. مقدار «زمان اضافهٔ تخمینی» صرفاً افزایش میانگین ضرب‌در تعداد اجرای اخیر است؛ صرفه‌جویی قطعی، مصرف CPU یا سود مالی نیست.

از میانگین و بیشینه نمی‌توان p95 واقعی اجراهای یک Query را بازسازی کرد. بنابراین داشبورد Query Store چنین عددی نمی‌سازد. p95 فقط در ابزار Lab و از نمونه‌های منفرد زمان کلاینت محاسبه می‌شود.

## ۵. تغییر Plan، شاهد است نه حکم قطعی

جزئیات شامل Plan ID، Plan Hash و وضعیت Forced Plan است. تغییر مجموعهٔ Planها بین دو پنجره علامت‌گذاری می‌شود؛ اما برنامه نمی‌گوید هر Plan جدید بدتر است یا باید Plan قبلی Force شود.

متن Query و XML Plan عمداً از Query Store انتخاب نمی‌شوند. مزیت این تصمیم، کاهش انتشار دادهٔ حساس است؛ هزینه‌اش این است که برای دیدن متن و درخت Plan، DBA باید با Query ID و دسترسی سازمانی از ابزار مناسب استفاده کند. تحلیل Operatorها، Plan Diff و پیشنهاد خودکار ایندکس در محدودهٔ این نسخه نیست.

## ۶. Blocking و Deadlock دو مسئلهٔ متفاوت‌اند

Blocking از درخواست‌های جاری نمونه‌برداری می‌شود. زنجیره تا ریشهٔ قابل مشاهده دنبال می‌شود؛ نشست خوابیده‌ای که تراکنش باز دارد، پایان زنجیرهٔ خارج از نمونه، چرخه و شناسهٔ مالک منفی به‌صورت وضعیت متفاوت ثبت می‌شوند. مقدار منفی `blocking_session_id` به‌اشتباه به یک Session قابل KILL تبدیل نمی‌شود. معنای این فیلدها در [مستند رسمی DMV](https://learn.microsoft.com/en-us/sql/relational-databases/system-dynamic-management-objects/sys-dm-exec-requests-transact-sql?view=sql-server-ver17) آمده است.

نمونه‌برداری هر ده ثانیه، تضمین مشاهدهٔ تمام Blockingهای کوتاه نیست. برای آن باید نیاز به XE اختصاصی و هزینهٔ جمع‌آوری جدا بررسی شود؛ برنامه چنین Sessionی را روی محیط عملیاتی خودکار ایجاد نمی‌کند.

Deadlock از فایل موجود `system_health*.xel` خوانده می‌شود. ورودی XML ممکن است موقتاً در حافظه شامل اطلاعات حساس باشد، اما خروجی ذخیره‌شده فقط ساختار محدودشدهٔ فرایندها، قربانی‌ها و مالک/منتظر منابع را نگه می‌دارد. SQL، نام ورود، میزبان و نام اشیای دیتابیس حذف می‌شوند. DTD و Resolver بیرونی غیرفعال‌اند و اندازه و تعداد عناصر محدود شده‌اند.

فایل‌های XE ممکن است Rotate شوند. سقف خروجی و Timeout نیز ممکن است پوشش را ناقص کنند. بنابراین «رویدادی دیده نشد» معادل «قطعاً Deadlock نداشته‌ایم» نیست. `TOP` تعداد خروجی را محدود می‌کند، نه الزاماً I/O خواندن فایل‌ها را. نسخهٔ فعلی Cursor پایدار برای XEL ندارد و بخشی از بازه را دوباره می‌خواند. [راهنمای system_health](https://learn.microsoft.com/en-us/sql/relational-databases/extended-events/use-the-system-health-session?view=sql-server-ver17).

## ۷. حداقل مجوز و محدودهٔ اعتماد

| منبع | SQL Server 2019 | SQL Server 2022 |
|---|---|---|
| Query Store در دیتابیس هدف | `VIEW DATABASE STATE` | `VIEW DATABASE PERFORMANCE STATE` |
| DMV و XEL انتخاب‌شده در سطح نمونه | `VIEW SERVER STATE` | `VIEW SERVER PERFORMANCE STATE` |

علاوه بر این مجوزها، Login/User و امکان اتصال لازم است. اسکریپت‌های پوشهٔ `sql/permissions/` باید توسط DBA بازبینی و اعمال شوند. مجوزهای دقیق XEL در [مستند تابع خواندن فایل](https://learn.microsoft.com/en-us/sql/relational-databases/system-functions/sys-fn-xe-file-target-read-file-transact-sql?view=sql-server-ver17) توضیح داده شده‌اند.

مجوزهای تشخیصی سرور، سطح دسترسی نمونه‌ای دارند و فقط به یک دیتابیس محدود نیستند. فیلتر خروجی در برنامه این واقعیت را تغییر نمی‌دهد. به همین دلیل Blocking و Deadlock در تنظیمات پیش‌فرض غیرفعال‌اند و باید آگاهانه فعال شوند.

اتصال وب نباید `sa`، `sysadmin` یا `db_owner` باشد. برنامه نام کاربری مستقیم `sa` را رد می‌کند، اما کشف تمام نقش‌های موروثی و حساب‌های ممتاز جای بازبینی DBA را نمی‌گیرد. `ApplicationIntent=ReadOnly` نیز فقط راهنمای مسیریابی است، نه مانع امنیتی اجرای Write.

## ۸. امنیت وب و نگهداری داده

کلید تصادفی حداقل ۳۲ کاراکتری در محیط سرور نگهداری می‌شود. پس از ورود، Cookie دارای HttpOnly و SameSite Strict استفاده می‌شود. درخواست‌های تغییر‌دهندهٔ نشست، CSRF و Origin کنترل‌شده دارند؛ Host نیز با PublicOrigin تطبیق داده می‌شود. ورود محدودیت نرخ دارد و خارج از Loopback استفاده از HTTPS الزامی است.

کلید در Local Storage مرورگر ذخیره نمی‌شود؛ تنها انتخاب زبان ذخیره می‌شود. Key Rotation نشست قبلی را نامعتبر می‌کند. پشت Reverse Proxy فقط IPهای مورد اعتماد باید معرفی شوند. کلیدهای Data Protection در پوشهٔ State هستند و روی Linux نباید رمزگذاری خودکار در حالت ذخیره را فرض کرد.

Snapshotها و حتی داده‌های پالایش‌شده می‌توانند از نظر سازمانی حساس باشند. رمزگذاری دیسک، ACL، پشتیبان، حذف ایمن و زمان نگهداری مسئولیت استقرار هستند. Export یک سند JSON بدون امضای دیجیتال است؛ هیچ ادعای گواهی غیرقابل‌تغییر یا اثبات حقوقی ندارد.

## ۹. آزمایش قابل بازتولید

ابزار `Observatory.Lab` فقط با گزینهٔ پذیرش صریح، نام دیتابیس `ObservatoryLab`، میزبان محلی مورد قبول، نسخهٔ Developer و Marker مورد انتظار کار می‌کند. نسخهٔ اصلی وب این ابزار را فراخوانی نمی‌کند. آدرس محلیِ Port Forward شده نیز باید واقعاً به نمونهٔ اختصاصی آزمایش اشاره کند.

دادهٔ اولیه شامل ۱۰۰ هزار ردیف مصنوعی است. سه مرحله با پارامترهای یکسان اجرا می‌شوند: ایندکس موجود، ایندکس حذف‌شده، ایندکس بازگردانده‌شده. هر مرحله پنج Warmup و سی اجرای اندازه‌گیری‌شده دارد. ابزار برابری خروجی‌ها را کنترل و نبود Logical Reads معتبر را شکست آزمایش تلقی می‌کند.

زمان کلاینت با Stopwatch شامل هزینهٔ شبکه و Driver است و جای زمان صرفاً موتور را نمی‌گیرد. Logical Reads از `STATISTICS IO` همان جدول دریافت می‌شود. Query Store نیز با Login محدودشده خوانده می‌شود. هم‌ترازکردن بازه‌ها اختیاری است، اما برای جداسازی سه مرحله توصیه شده است؛ Warmupها یا دستورات دیگر ممکن است در Bucketهای ثبت‌شده حضور داشته باشند.

هیچ `DBCC FREEPROCCACHE` یا پاک‌سازی سراسری Cache اجرا نمی‌شود. درصد بهبود ازپیش‌ساخته وجود ندارد و ممکن است آزمایش روی سیستم سریع، آستانهٔ افزایش ۲۵ میلی‌ثانیه‌ای داشبورد را رد نکند. این نتیجه شکست روش اندازه‌گیری نیست؛ باید زمان، تعداد خواندن‌ها و شرایط اجرا را همان‌طور که هستند گزارش کرد.

سناریوهای جدا برای Blocking واقعی، Deadlock واقعی و اثبات محدودبودن Login خواننده وجود دارند. گرفتن دقیق یک خطای SQL 1205 و مشاهدهٔ رویداد XEL بخشی از پذیرش Deadlock است؛ آیکون نمایشی در داشبورد به‌جای آن محسوب نمی‌شود. [دستورهای کامل آزمایش](en/lab-guide.md).

## ۱۰. انتشار و ارائهٔ حرفه‌ای در GitHub

ریشهٔ ZIP همان ریشهٔ Repository است. README انگلیسی، نسخهٔ آلمانی، راهنمای نصب، معماری، سه ADR، روش تحلیل، امنیت، مجوزها، API، عملیات، آزمایش، برنامهٔ توسعه و نمونهٔ ارائهٔ پورتفولیو داخل آن قرار دارند. تصاویر رابط نیز با دادهٔ مصنوعی و بدون اطلاعات مشتری تهیه شده‌اند.

دو Workflow ارائه شده است: Verify برای بررسی سورس، Build، xUnit و آزمون مرورگر روی میزبان واقعی ASP.NET؛ و آزمایش SQL اختیاری برای اجرای سناریوهای واقعی روی کانتینر اختصاصی Developer. این Workflowها نوشته شده‌اند، نه اینکه اجرای موفق آن‌ها در GitHub ادعا شود.

مسیر مناسب برای رزومه، ثبت یک انتشار واقعی پس از عبور Build و Lab است: معرفی فرضیه، نشان‌دادن شاهد کندی، توضیح علت انتخاب اصلاح، اجرای دوبارهٔ همان بار و ثبت محدودیت‌های نتیجه. Badge سبز یا درصد بهبود باید فقط از اجرای واقعی بیاید. اسکرین‌شات به‌تنهایی شاهد صحت آداپتور SQL نیست.

## ۱۱. مسیر توسعهٔ بعدی

اولویت نخست، Build و پذیرش واقعی روی SQL Server 2022 Developer و سپس نسخهٔ هدف سازمان است. بعد از آن می‌توان Cursor پایدار XEL، هویت دیتابیس مقاوم‌تر در برابر Restore، آرشیو سری‌زمانی، رابط تاریخچه، سنجش هزینهٔ Collector و محدودکردن بیشتر دسترسی از طریق رویه‌های امضاشده را بررسی کرد.

SSO، نقش‌های مجزا، چندنمونه‌ای، هشدار بیرونی، SQL Azure و تحلیل کامل Plan باید پروژهٔ مرحلهٔ بعد باشند؛ اضافه‌کردن ظاهری این عنوان‌ها پیش از داشتن تست، ارزش مهندسی ندارد. AI نیز فقط زمانی ارزشمند است که روی شواهد مجاز، با ارزیابی قابل اندازه‌گیری و بدون مجوز تغییر خودکار کار کند.

**معیار موفقیت نسخهٔ نخست:** یک بررسی‌کننده بتواند پروژه را Build کند، آزمایش محدود را اجرا کند، نتیجهٔ واقعی را بازبینی کند و بفهمد برنامه چه چیزی می‌داند و چه چیزی را نمی‌داند.
